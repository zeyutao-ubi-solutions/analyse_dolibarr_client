# 公司 lookalike 模型

> 状态（2026-11-20）：标签和样本已就绪；LinkedIn 抓取进行中；训练模块在分支 `lookalike-training` 开发中。
> 特征的细节规则以 [`docs/labeling/feature_policy.md`](../labeling/feature_policy.md) 为准，本文件讲整体设计、使用和运维。

## 1. 要回答的问题

**只看一家公司在 LinkedIn 上的公开信息，它像不像我们的终端客户？像的话，该推哪条业务线？**

- 用来给 web app 找到的公司、Dolibarr 里从没成交的潜在客户、外部名单排序。
- 只用 LinkedIn 信息，是因为潜在客户在我们这里没有任何订单数据；模型对客户和潜在客户必须用同一套信息。

## 2. 业务线

业务范围是硬件 + 软件，归为三条线（Connected Things 是定位的软件平台，和定位算同一条）：

| 业务线 | id | 识别方式 |
|---|---|---|
| Géolocalisation / Connected Things | `geoloc` | Dolibarr 产品标签 `UBI Solutions > GPSBLE`；没有标签的老产品按名称规则（tracker、beacon、LoRa、géolocalisation…） |
| Traçabilité | `rfid` | RFID 子品类、名称（RFID、UHF、UBITex…）、制造商（Fenotag、Impinj、Feig）、RFID 相关标签 |
| Ubi Cloud | `ubi_cloud` | 产品名含 UBI Cloud |

web app 原来按产品目录（市场部的行业 / 产品包装）分类，已确认不再使用。

## 3. 样本与标签

数据来自 `data/processed/<snap>/labeling/lookalike_units.csv`（`lookalike.py` 生成）。2026-11-18 快照的数字：

| | 数量 | 说明 |
|---|---:|---|
| 样本单元 | 9,712 | 一个单元 = LinkedIn 视角下的一家公司：同一网站域名为一个单元，没有域名的按第三方 |
| 正样本 `positive` | 897 | 终端客户，订单金额 > 0 |
| 未标注 `unlabeled` | 8,648 | Dolibarr 里从没成交的潜在客户。**不是负样本**：可能只是没人跟进 |
| 排除 `excluded` | 167 | 集成商 / 经销商、订单金额为 0、只是供应商 |
| 分配模型样本 `in_allocation_set` | 564 | 买过至少一条业务线的客户单元：定位 204、RFID 366、Ubi Cloud 135（可重叠） |

- **客户类型**：疑似集成商、同时是供应商、订单名和档案名不同的 125 家（P1）需要人工复核，见 [`customer_type.md`](../labeling/customer_type.md)。集成商混进正样本会让模型学成「找集成商」。
- **国家**：正样本 81% 在法国。国家**不是特征**；未标注样本按国家重新加权（`sample_weight`），使其国家分布与正样本一致。排序时再乘可人工调整的国家系数（`country_factors.csv`）。
- **价值档位** `value_tier`（core / standard / immature / truncated）：按首单后 24 个月的消费，留给以后的价值模型和样本加权用，当前模型不用。
- **切分**：`split_group` 按集团分组（同一域名不能同时在训练集和测试集）；`cohort_year` 用于按时间验证。

## 4. 模型结构

```
第 1 步  总模型（PU）       像不像我们的客户？          → fit_overall
第 2 步  分配模型（多标签）  如果是客户，会买哪几条线？   → p_geoloc, p_rfid, p_ubi_cloud
对照     kNN 相似度         最像哪几家已有客户？         → nearest_customers，也作为基线

某条线的分数 = fit_overall × p_该线
排序优先级   = fit_overall × country_factor
```

为什么不是每条线一个模型：定位和 Ubi Cloud 正样本太少；Ubi Cloud 几乎都和硬件一起买，单独建模会学成「是不是买硬件的客户」。分配模型只在客户内部比较，三条线共用 564 个客户。

## 5. 特征

**主特征是公司简介**（description + tagline + specialties），LinkedIn 行业字段由公司自选，常常不准或太宽，只作辅助。辅助特征还有员工规模、公司类型、成立年份、关注者数、地点数量、是否有母公司。

禁止：总部国家 / 城市、地点列表、网站域名、文本语言、公司名称和法律形式、电话，以及任何 Dolibarr 字段（金额、品类、价值档位…）。完整清单和原因见 `feature_policy.md`。

## 6. 技术选型

| 部分 | 选择 | 理由 |
|---|---|---|
| 文本向量 | fastembed（ONNX，不需要 torch）+ 多语言 e5 系列，本机运行 | 多语言同义文本落在同一位置；数据不出本机；可复现 |
| 向量模型大小 | 在 e5-large / base / small 和 large 的 int8 量化版之间，用真实数据比较后选：AUC 与最好者相差 ≤ 0.02 的模型里选内存最小的 | large 运行时约 2.5–3GB 内存，small 约 0.5GB（估算，以实测为准） |
| 分类器 | scikit-learn 逻辑回归（L2，正则强度由分组交叉验证选） | 样本约 3,000、向量上千维，线性模型最稳；系数可导出 |
| PU 方法 | 未标注当负样本训练，带国家权重，分数只用于排序 | v1 最简单可靠 |
| 模型文件 | `model.json` + `customers_index.npz`，**不用 pickle** | 打分只需要 numpy + fastembed；pickle 加载可执行任意代码 |

## 7. 训练流程

1. 合并：样本单元 + LinkedIn 结果（只用 `matched`，以及人工确认过的 `ambiguous`），重算国家权重。
2. 匹配偏差检查：比较正样本和未标注样本的匹配率、匹配方式、集团页比例。差异大时，模型可能学到的是「匹配方式不同」。
3. 生成特征：文本向量（带缓存）+ 结构化特征（白名单）。
4. 国家泄漏检查：用同一套特征预测国家。明显好于「全猜法国」时，对向量做按语言去中心化后重做。
5. 训练总模型、分配模型、kNN 对照。
6. 验证（第 8 节），写 `report.md` 和 `metrics.json`。
7. 写模型文件（带版本号），给所有抓到的潜在客户打分。

## 8. 验证和上线标准

| 检查 | 方法 | 上线要求（首轮结果出来后可调整） |
|---|---|---|
| 排序能力 | 按集团分组的交叉验证：AUC、平均精度、前 10% / 20% 召回率和提升倍数 | 明显好于随机；FR、ES 分别报告 |
| 按时间验证 | 用 2024 年及以前的客户训练，看 2025–2026 年新客户能否排在潜在客户前面 | AUC 明显高于 0.5，且和交叉验证结果相差不大 |
| 对照比较 | 逻辑回归 vs kNN | 逻辑回归不差于 kNN，否则上线 kNN |
| 国家泄漏 | 预测 `country_bucket` 的平衡准确率 vs 基线 | 接近基线 |
| 分配模型 | 每条线的 AUC / 平均精度 | Ubi Cloud 样本少，只要求方向正确 |
| 匹配偏差 | 正样本 vs 未标注的匹配方式分布 | 无明显系统差异，或已在报告里说明影响 |

说明：未标注样本里混有潜在的客户，所以这些指标都是真实效果的**下限**。

## 9. 输出

每家公司：

| 字段 | 含义 |
|---|---|
| `fit_overall`、`fit_percentile` | 像不像客户；展示用百分位（「前 8%」），不要展示成成交概率 |
| `p_geoloc`、`p_rfid`、`p_ubi_cloud` | 推哪条线 |
| `country_factor`、`priority` | 国家系数、排序优先级 |
| `nearest_customers` | 最像的 3 家已有客户（可解释） |
| `thin_page` | 简介太少，分数仅供参考 |
| `model_version` | 追溯和回退用 |

## 10. 怎么用

1. **评估新公司**（web app 主场景）：抓取 LinkedIn 后打分，显示匹配度、推哪条线、最像哪几家客户、可信度提醒。替代原来大模型按产品目录给的固定区间分数；大模型仍可用这些结果写开发信。
2. **给现有潜在客户排序**：Dolibarr 里约 10,000 个潜在客户批量打分，按国家和业务线出名单。
3. **交叉销售**：已买某条线的客户，看其他线的 `p_*`。用交叉验证的预测值，不用模型在训练样本上的打分。
4. **评估外部名单**：展会名单、行业名录等，抓 LinkedIn 后批量打分。

使用原则：

- 分数是排序依据，不是成交概率。
- 不自动淘汰低分公司：低分只说明「不像以往的客户」，模型找不出全新行业。
- 国家系数随策略调整，不用重新训练。
- 集成商 / 同行由销售判断，模型分不出来。

## 11. 部署

| 方案 | 做法 | 资源 | 适合 |
|---|---|---|---|
| 批量文件交换 | web app 导出 → 本仓库打分 CLI → 导回 | 无额外服务器 | 上线初期，先让销售验证几周 |
| 嵌入 web app 后端 | 后端安装 numpy + fastembed，加载模型文件实时打分 | 增加向量模型的内存（按选定模型，约 0.5–3GB）和硬盘 | 效果确认后，web app 在云上且可以加内存 |
| 独立打分服务 | 单独的 FastAPI 小服务，web app 通过 HTTP 调用 | 一台常开的机器（16GB 的 Apple Silicon 足够） | web app 不想引入机器学习依赖，或多个系统共用 |

常开电脑方案的要求：关闭睡眠；launchd 开机自启、崩溃重启；web app 在云上时用 Tailscale / Cloudflare Tunnel，不直接暴露端口，接口带访问令牌；服务只读模型文件、不读 `data/`；单独系统账户、开启 FileVault；web app 侧在服务不可用时排队重试。

**待决定**：web app 生产环境部署在哪里（云服务器 / 本地或办公室机器），决定选哪种方案。

## 12. 反馈回流

最重要的长期工作。web app 需要为每家打过分的公司记录：

| 字段 | 说明 |
|---|---|
| `unit_id` / LinkedIn URL | 对应哪家公司 |
| 打分时的 `fit_overall`、`p_*`、`model_version`、展示时间 | 以后才能区分「模型推荐得好」还是「销售本来就会联系」 |
| 跟进状态 | 联系了 → 有回复 → 约到会议 → 成交 / 丢单 |
| 不相关原因 | 集成商、同行、规模太小、行业不对、已有方案… |
| 推的业务线 | 实际推了哪条线 |

有了「联系过但明确不合适」的记录，就有了真正的负样本：模型可以从 PU 学习升级为普通的有监督学习，并第一次能计算真实的准确率。

## 13. 更新与监控

- **重新训练**：每季度或每次新快照。新快照 → 重建客户名单 → 重建样本单元 → 只抓新增单元 → 训练新版本 → 和上一版比较指标 → 更好才替换。
- **监控**：分数分布的变化、`thin_page` 比例、LinkedIn 抓取格式变化（actor 升级）、匹配率。
- **刷新**：已抓的主页约一年刷新一次。
- **人工复核**：P1 客户类型复核完成、人工匹配队列处理后，重新训练。

## 14. 局限

- 学的是「以往卖给了谁」，带着销售历史的偏差（法国为主、以往重点行业）。
- 定位的正样本大多是 2025–2026 年的小额试点，`p_geoloc` 学的是「谁愿意试」。
- Ubi Cloud 多为硬件客户的加购，`p_ubi_cloud` 的含义是「谁会加购」。
- 新行业、新业务线需要先靠人工积累客户。
- LinkedIn 简介是公司自己写的营销文字，质量不一。

# Company lookalike model

> Status (2026-11-20): labels and samples are ready; LinkedIn scraping in progress; training module under development on branch `lookalike-training`.
> Detailed feature rules are governed by [`docs/labeling/feature_policy.md`](../labeling/feature_policy.md); this file covers overall design, usage and operations.

## 1. The question

**Looking only at a company's public LinkedIn information, does it resemble our end customers? If so, which business line should we pitch?**

- Used to rank companies found by the web app, Dolibarr prospects that never bought, and external lists.
- LinkedIn information only, because prospects have no order data with us; the model must use the same information for customers and prospects.

## 2. Business lines

The business covers hardware + software, grouped into three lines (Connected Things is the geolocation software platform and counts as the same line as geolocation):

| Business line | id | How identified |
|---|---|---|
| Géolocalisation / Connected Things | `geoloc` | Dolibarr product tag `UBI Solutions > GPSBLE`; untagged older products by name rules (tracker, beacon, LoRa, géolocalisation…) |
| Traçabilité | `rfid` | RFID subcategories, names (RFID, UHF, UBITex…), manufacturers (Fenotag, Impinj, Feig), RFID-related tags |
| Ubi Cloud | `ubi_cloud` | Product name contains UBI Cloud |

The web app's original classification by product catalogue (marketing's industry / product packaging) is confirmed as no longer used.

## 3. Samples and labels

Data comes from `data/processed/<snap>/labeling/lookalike_units.csv` (generated by `lookalike.py`). Figures for the 2026-11-18 snapshot:

| | Count | Notes |
|---|---:|---|
| Sample units | 9,712 | One unit = one company from LinkedIn's point of view: the same website domain is one unit; without a domain, by third-party record |
| Positive `positive` | 897 | End customers, order amount > 0 |
| Unlabelled `unlabeled` | 8,648 | Dolibarr prospects that never bought. **Not negatives**: perhaps nobody followed up |
| Excluded `excluded` | 167 | Integrators / resellers, order amount 0, supplier only |
| Allocation model samples `in_allocation_set` | 564 | Customer units that bought at least one business line: geolocation 204, RFID 366, Ubi Cloud 135 (may overlap) |

- **Customer type**: 125 suspected integrators, customers that are also suppliers, or with order name differing from the third-party record name (P1) need manual review, see [`customer_type.md`](../labeling/customer_type.md). Integrators mixed into the positives would teach the model to "find integrators".
- **Country**: 81% of positives are in France. Country is **not a feature**; unlabelled samples are reweighted by country (`sample_weight`) so their country distribution matches the positives. At ranking time, a manually adjustable country factor (`country_factors.csv`) is applied.
- **Value tier** `value_tier` (core / standard / immature / truncated): by spend in the 24 months after the first order; kept for a future value model and sample weighting, not used by the current model.
- **Split**: `split_group` groups by corporate group (the same domain cannot be in both training and test sets); `cohort_year` is for time-based validation.

## 4. Model structure

```
Step 1   Overall model (PU)         Does it resemble our customers?          → fit_overall
Step 2   Allocation model (multi-label)  If a customer, which lines would it buy?  → p_geoloc, p_rfid, p_ubi_cloud
Baseline kNN similarity             Which existing customers is it most like?  → nearest_customers, also a baseline

Score for a line   = fit_overall × p_<line>
Ranking priority   = fit_overall × country_factor
```

Why not one model per line: geolocation and Ubi Cloud have too few positives; Ubi Cloud is almost always bought with hardware, so modelling it alone would learn "is this a hardware customer". The allocation model compares only within customers, and the three lines share 564 customers.

## 5. Features

**The main feature is the company description** (description + tagline + specialties). The LinkedIn industry field is self-selected by the company, often inaccurate or too broad, and is only auxiliary. Other auxiliary features: employee size, company type, founding year, follower count, number of locations, whether it has a parent company.

Forbidden: headquarters country / city, location list, website domain, text language, company name and legal form, phone, and any Dolibarr field (amounts, categories, value tier…). Full list and reasons in `feature_policy.md`.

## 6. Technical choices

| Part | Choice | Reason |
|---|---|---|
| Text embeddings | fastembed (ONNX, no torch needed) + multilingual e5 family, run locally | Synonymous texts in different languages land in the same place; data stays on the machine; reproducible |
| Embedding model size | Chosen among e5-large / base / small and the int8-quantised large by comparing on real data: among models within ≤ 0.02 AUC of the best, pick the one with the smallest memory | large needs about 2.5–3GB of memory at runtime, small about 0.5GB (estimates, to be measured) |
| Classifier | scikit-learn logistic regression (L2, regularisation strength chosen by grouped cross-validation) | About 3,000 samples and thousand-plus-dimensional embeddings: a linear model is the most stable; coefficients can be exported |
| PU method | Train with unlabelled as negatives, with country weights; scores used only for ranking | Simplest and most reliable for v1 |
| Model files | `model.json` + `customers_index.npz`, **no pickle** | Scoring needs only numpy + fastembed; loading a pickle can execute arbitrary code |

## 7. Training pipeline

1. Merge: sample units + LinkedIn results (only `matched`, plus manually confirmed `ambiguous`), recompute country weights.
2. Match-bias check: compare match rate, match method and share of group pages between positives and unlabelled samples. If they differ a lot, the model may learn "different match method".
3. Build features: text embeddings (cached) + structured features (allowlist).
4. Country-leak check: predict country from the same features. If clearly better than "always guess France", de-centre the embeddings by language and redo.
5. Train the overall model, the allocation model and the kNN baseline.
6. Validate (section 8), write `report.md` and `metrics.json`.
7. Write model files (versioned) and score all scraped prospects.

## 8. Validation and release criteria

| Check | Method | Release requirement (adjustable after the first results) |
|---|---|---|
| Ranking ability | Cross-validation grouped by corporate group: AUC, average precision, recall and lift at top 10% / 20% | Clearly better than random; FR and ES reported separately |
| Time-based validation | Train on customers up to 2024, check whether new 2025–2026 customers rank above prospects | AUC clearly above 0.5, and not far from the cross-validation result |
| Baseline comparison | Logistic regression vs kNN | Logistic regression no worse than kNN, otherwise release kNN |
| Country leak | Balanced accuracy for predicting `country_bucket` vs baseline | Close to baseline |
| Allocation model | AUC / average precision per line | Ubi Cloud has few samples; only the right direction is required |
| Match bias | Distribution of match methods, positives vs unlabelled | No clear systematic difference, or its impact explained in the report |

Note: the unlabelled samples contain hidden customers, so all these metrics are a **lower bound** on real performance.

## 9. Output

For each company:

| Field | Meaning |
|---|---|
| `fit_overall`, `fit_percentile` | How much it resembles a customer; display the percentile ("top 8%"), not as a probability of closing |
| `p_geoloc`, `p_rfid`, `p_ubi_cloud` | Which line to pitch |
| `country_factor`, `priority` | Country factor, ranking priority |
| `nearest_customers` | The 3 most similar existing customers (explainability) |
| `thin_page` | Description too short, score indicative only |
| `model_version` | For traceability and rollback |

## 10. How to use

1. **Evaluate new companies** (main web app scenario): score after scraping LinkedIn, show fit, which line to pitch, most similar customers, and a reliability warning. Replaces the fixed-range scores the LLM gave from the product catalogue; the LLM can still use these results to write outreach emails.
2. **Rank existing prospects**: batch-score the roughly 10,000 prospects in Dolibarr and produce lists by country and business line.
3. **Cross-selling**: for customers who already bought one line, look at the other lines' `p_*`. Use cross-validated predictions, not the model's scores on its training samples.
4. **Evaluate external lists**: trade-show lists, industry directories, etc.; scrape LinkedIn and batch-score.

Usage principles:

- The score is a basis for ranking, not a probability of closing.
- Low-scoring companies are not eliminated automatically: a low score only means "unlike past customers", and the model cannot find entirely new sectors.
- Country factors follow strategy and need no retraining.
- Integrators / peers are for sales to judge; the model cannot tell them apart.

## 11. Deployment

| Option | Approach | Resources | Suited to |
|---|---|---|---|
| Batch file exchange | web app export → this repo's scoring CLI → import back | No extra server | Early rollout, letting sales validate for a few weeks first |
| Embedded in the web app backend | Install numpy + fastembed in the backend, load the model files and score in real time | Extra memory for the embedding model (about 0.5–3GB depending on the chosen model) and disk | Once results are confirmed, if the web app is in the cloud and memory can be added |
| Standalone scoring service | A small separate FastAPI service, called by the web app over HTTP | One always-on machine (a 16GB Apple Silicon is enough) | If the web app should not take on machine-learning dependencies, or several systems share it |

Requirements for the always-on computer option: sleep disabled; launchd for start at boot and restart on crash; if the web app is in the cloud, use Tailscale / Cloudflare Tunnel rather than exposing ports directly, with an access token on the API; the service reads only the model files, never `data/`; a separate system account, FileVault on; on the web app side, queue and retry when the service is unavailable.

**To decide**: where the web app's production environment is deployed (cloud server / local or office machine) determines which option to choose.

## 12. Feedback loop

The most important long-term work. For each scored company, the web app needs to record:

| Field | Notes |
|---|---|
| `unit_id` / LinkedIn URL | Which company |
| `fit_overall`, `p_*`, `model_version` at scoring time, display time | Needed later to tell "the model recommended well" from "sales would have contacted them anyway" |
| Follow-up status | Contacted → replied → meeting booked → won / lost |
| Not-relevant reason | Integrator, peer, too small, wrong sector, already has a solution… |
| Line pitched | Which line was actually pitched |

With records of "contacted but clearly not a fit", there are real negatives: the model can move from PU learning to ordinary supervised learning, and real accuracy can be computed for the first time.

## 13. Updates and monitoring

- **Retraining**: every quarter or with each new snapshot. New snapshot → rebuild customer list → rebuild sample units → scrape only new units → train new version → compare metrics with the previous version → replace only if better.
- **Monitoring**: shifts in score distribution, `thin_page` share, LinkedIn scraping format changes (actor upgrades), match rate.
- **Refresh**: scraped pages refreshed about once a year.
- **Manual review**: retrain after the P1 customer-type review is done and the manual matching queue is processed.

## 14. Limitations

- It learns "who we sold to in the past", carrying the biases of sales history (mostly France, historically focused sectors).
- Geolocation positives are mostly small 2025–2026 pilots, so `p_geoloc` learns "who is willing to try".
- Ubi Cloud is mostly an add-on for hardware customers, so `p_ubi_cloud` means "who will add it on".
- New sectors and new business lines first need customers built up manually.
- LinkedIn descriptions are marketing text written by the companies themselves, of uneven quality.
